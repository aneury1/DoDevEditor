# DoDevEditor wxWidgets 5.1.4 — VSCode task variables

The task selector beside Theme and Terminal > Run Task / Run Build Task share the same planner. Values are resolved at execution time, after workspace approval. One input value per variable is reused during a dependency plan; cancelling any prompt prevents all task launches. A subsequent run prompts again. Existing JSONC handling, toolbar refresh and installed wxWidgets RUNPATH are retained.

## Supported variables

Existing `${workspaceFolder}`, `${workspaceRoot}`, `${workspaceFolderBasename}`, `${file}`, `${fileDirname}`, `${fileBasename}`, `${fileBasenameNoExtension}`, `${fileExtname}`, `${relativeFile}`, `${relativeFileDirname}`, `${lineNumber}`, `${columnNumber}`, `${selectedText}`, `${env:NAME}`, `${userHome}`, `${pathSeparator}`, `${/}` remain supported. Added `${fileWorkspaceFolder}`, `${fileDirnameBasename}`, `${execPath}` (DoDevEditor executable, not VSCode), `${cwd}` (startup working directory where available), `${defaultBuildTask}`, `${workspaceFolder:NAME}` (currently opened folder only), `${config:KEY}`, `${input:ID}` and explicitly mapped `${command:ID}`.

`${config:KEY}` first looks in workspace `.vscode/settings.json` (JSONC, flat or nested scalar values), then in DoDevEditor settings for GUI tasks. Unknown settings are errors. The editor does not import VSCode's user settings or extension defaults. Missing environment variables expand to empty strings, as before. Only command, args and options are expanded. Labels and input definitions are literal. No recursive substitutions within resolved values.

Inputs support `promptString` (including a masked password field), `pickString` (string or label/value options and default), and `command` with a manually mapped result. Command IDs are not executed; VSCode extensions are not loaded. Set a mapping in `.vscode/settings.json`:

```json
{
  "dodev.taskCommandVariables": {
    "cmake.launchTargetPath": "/absolute/path/to/build/myapp"
  }
}
```

The value is a literal, not another variable expression. Command input `args` are not executed or interpreted. For arbitrary extension command support, use a future command provider. A masked input is NOT a secret-storage facility: values may appear in process arguments, environment and task output. Never use this feature for sensitive credentials; the UI warns before accepting a masked input.

See `examples/task-variables/.vscode/` for a runnable sample. Open that folder, select `Show variables` or `Build example`, click Run Task and approve the workspace. For ordinary shell commands, simple POSIX quote contexts are supported; prefer `type: process` and separate `args` for paths and user input. Windows raw shell interpolation is rejected; use process tasks. Complex shell syntax (heredocs, nested substitutions, custom shell dialects) is not fully supported.

## GDB

The GDB preLaunchTask generator uses the same task planner for static variables, workspace settings, mapped commands, and sequential dependencies. `${defaultBuildTask}` is supported as a preLaunchTask label. Native plugin interactive input prompts, current selection/column, editor executable/startup cwd and application settings fallback are not passed through the GDB host ABI; for interactive tasks run the build through the toolbar first. The launch.json parser itself has not been replaced. GDB still runs its pre-launch process list inside GDB Python; a failing command aborts automatic debugger setup.

## Validation

Headless Debug build and four targeted CTest cases passed: `vscode_task_variables`, `vscode_terminal_tasks`, `workspace_task_catalog`, `gdb_configuration_and_native_plugin`. wxWidgets development headers are unavailable in the build environment; GUI compilation and live dialogs are not verified. Full test suite not rerun. Parallel/background tasks, problem matchers, multi-root workspaces, and extension commands remain outside the supported subset.
